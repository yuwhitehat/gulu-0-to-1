## 概述

**骨碌（Gulu）** 是 ToC **主动聊天 AI「灵魂盲盒」**产品。用户首次进入抽取 1 张 E 型人格卡（ENFJ / ENFP / ENTJ / ENTP），AI 以该人格**主动**找用户聊天、碰撞热搜、随互动升温关系、积累长期记忆。

- 核心特色：**主动**、**随机人格**（盲盒宿命感）、**热搜碰撞**、**长期关系**（stranger → familiar → intimate）；

- 商业闭环：**首次免费抽取 → 付费重抽（1 元/次，最多共 3 张卡）→ 会员（9\.9 元首月，次月 29 元/月）**。

## 一、完整目录树

> 本设计的对象是**应用本体（****`workspace/`****，只读）**。本地运行包形态为 `user/`（用户态，可写）\+ `workspace/`（应用本体）\+ 包根启动引导 `AGENTS.md` / `start.sh`。

```
workspace/                          # 应用本体（只读）
├── AGENTS.md                       # 应用入口：读写契约 / Turn 顺序 / Skill 路由 / 红线 / 定时任务（创建方式 + 触发后投递）
├── manifest.dev.json               # 发布清单（app_name=Gulu）
├── onboarding.md                   # 用户首次使用引导
│
├── .codex/skills/                  # 7 个应用内 Skill（各含 SKILL.md + scripts/，共 35 文件）
│   ├── intro/                      # collect_user_info / init_state / persona_draw / set_proactive_consent
│   ├── dialogue/                   # analyze_scene / build_strategy / detect_mode / advance_stage
│   ├── response/                   # orchestrate_turn / persona_render / pre_send_check / recall_memory / record_interaction
│   ├── proactive-message/          # should_disturb / send（只组装＋热搜去重，不发送）/ setup_schedule / ensure_schedules / confirm_schedules
│   ├── billing/                    # redraft_engine / retention / payment / member_manager / apply_membership / apply_redraft
│   ├── memory-curator/             # curate_memory / correct_memory / check_freeze
│   └── life-event-generator/       # generate_life_events
│
├── scripts/                        # 公共脚本（5）
│   ├── safety_filter.py  load_context.py  llm_generate.py
│   ├── interaction_signal.py  state_store.py
│   └── schedules/                  # 定时确定性入口（4）：check_trigger / curate_memory / generate_life_events / _sched_common
│
├── knowledge/                      # 知识底座（只读）
│   ├── hotsearch/mock-topics.json
│   ├── personas/{enfj,enfp,entj,entp}/{card,interests,stage-boundaries}.json

├── memory/                         # 记忆策略与模板（只读）

**设计思路**：记忆文件**初始作为模板放在 Workspace 侧的 ****`memory/templates/`**（只读）；**用户完成引导、绑定人格后**，由 `intro/init_state` **从模板实例化到 ****`UserDir/`**，成为该用户私有记忆（当前群私有、可写）。

**Workspace 侧（只读）**

|位置|内容|
|---|---|
|`memory/README.md`|记忆策略（文件语义、读写与衰减合同、不存什么）|

**UserDir 侧（每用户私有，绑定后由模板实例化）**

```
UserDir/

**文件语义与衰减**

|文件|内容|写入者|读取者|衰减|
|---|---|---|---|---|
|`state.md`|关系阶段 / 互动模式 / 计数 / 投诉标记 / 未成年保护 / 记忆冻结 / 会员状态 / 主动许可 / 定时任务状态|intro · response · billing · memory\-curator|全部 Skill|只推进，不衰减|

## 六、定时触发（**动态工具创建 \+ ****`silent`**** 投递 / 门禁通过显式发送**）

### 6\.1 设计原则

1. 应用**不直连、不持凭证、文档里不出现任何外部地址**；

2. 创建 / 列举 / 更新**只用 Bot 运行时注入的动态工具**——`schedule.create`（`kind` = `prompt` \| `script`）、`schedule.list_own`、`schedule.update`；**不得采用其它任何方式**；

3. 应用**输出任务请求**（`setup_schedule`），由**运行态 Agent 用动态工具创建**；创建回执经 `confirm_schedules` 回写 `state.schedule_tasks`；

4. 任务类型 = **`kind=prompt`**（到点唤起运行态 Agent 并递上固定 Prompt）；平台开脚本能力后可切 `kind=script`（脚本已在 `scripts/schedules/`）；

5. 主动消息用 **`interval`**** / fixed\-delay**，**不写成五段 Cron**；每日任务用 `cron`；

6. **投递（v0\.38，方案 A）**：proactive 任务用 **`delivery_mode=silent`** —— 平台**不投递**任何结果；**门禁通过时由 Agent 显式调用一次 ****`feishu.message_send_current_channel`**** 发一条角色消息**，**门禁不通过 → 零动作、零输出**（群里零动静）。

    - 为什么不用 `notify`：`notify` 会在**每次唤醒**（含「门禁不通过」）都投递结果 → 群里出现「本次为定时主动检查，门禁未通过…」这种**出戏消息**（曾出现「门禁不通过也刷群」的问题，已由 `silent` \+ 显式发送修掉）。

### 6\.2 三个定时任务（创建参数）

|任务|`name`|`trigger`|`action.prompt`（`kind=prompt`）|`delivery_mode`|`idempotency_key`|
|---|---|---|---|---|---|
|**主动触达**|骨碌\-主动消息|interval / fixed\-delay **660s（验证档；正式档 5280s = 88min）**|`gulu proactive-reach check`|**`silent`****（平台不投递；要发由 Agent 显式发一条）**|`gulu-proactive-v1`|
|**记忆整理**|骨碌\-记忆整理|cron `30 0 * * *`（Asia/Shanghai）|`gulu memory-curate daily`|`silent`|`gulu-curate-v1`|
|**AI 生活编造**|骨碌\-生活事件|cron `0 2 * * *`（Asia/Shanghai）|`gulu life-event daily`|`silent`|`gulu-life-event-v1`|

- `delivery_mode` 语义：**本应用用 ****`silent`**（平台不投递 → 不发时零动静）；**不要用 ****`notify`**（每次唤醒都投递结果，会出戏）。

- `silent` 的两条任务**不产生用户可见输出**（只做内部整理 / 生成）。

- `idempotency_key` 稳定 → 重试 / 补建**不会重复建任务**；按 `task_type` 复用。

- 用户明确拒绝主动消息（`proactive_allowed=false`）→ **不产出 proactive 任务**，且门禁兜底不发；另两条照常。

### 6\.3 触发后的执行链路

1. 平台到点 → 把固定 prompt 递给运行态 Agent；

2. Agent 按 `AGENTS.md`「Prompt → 动作」跑 `scripts/schedules/` 下对应脚本；

3. **主动触达**：`check_trigger.py` 先过门禁（见 6\.4）→ 通过则组装 `reply_text`（**热搜去重 \+ 轮换**，见 6\.5）返回；

4. **门禁通过** → Agent 显式调用一次 `feishu.message_send_current_channel`，把 `reply_text` 作为**一条角色语言消息**发到当前群（任务为 `silent`，平台不自动投递，只发这一条）；

5. **门禁不通过** → 结束本次 run、**零动作、零输出**（"不发"是正常且最常见的结果，群里必须零动静）；

6. 状态：`unanswered_count` / `last_proactive_at` 由 `record_interaction` 落盘；**投递无回执，应用不记录送达结果**。

### 6\.5 热搜内容去重（v0\.39）

连续两次主动消息**不得复用同一条热搜**：

1. `send` 读 `state.hotsearch_recent`（最近 10 条 id）→ **优先排除最近用过的**；

2. 再用 **n\-gram（4 连字）与近期主动消息**（`timeline.jsonl` 里 `type=proactive` 的 `ai_message`）比对，命中则跳过；

3. 池子用尽 → 取**最久没用过的**（轮换，保证仍能发）；

4. 选中后**回写** `hotsearch_recent`（去重追加、截断 10 条）；无匹配仍降级为性格闲聊（content\_hint=B）。

> 动机：接入真实热搜后，热门话题会长时间霸榜 —— 没有去重/轮换就会连续两次聊同一条（v0\.37 实跑已复现）。

### 6\.4 主动消息门禁（按序，任一不过即不发）

1. **用户许可**：`proactive_allowed=false` → 不发（未明确回答 → 默认发）；

2. **投诉即停**：`complaint_flag` → 不发；

3. **安静时段**：23:00–08:00 → 不发（顺延早上）；

4. **间隔**：距上次互动未满（**验证档 J=20min / P=10min；正式档 J=2h / P=100min**）→ 不发；

5. **降频**：连续未回复 ≥3 → 间隔翻倍；

6. **未成年**：最低间隔 ≥2h。

## 七、验证档 vs 正式档（**差异对照**）

同一套代码，只差**三个常量 \+ 文档标注**。**验证档只用于 Owner 快速验证，上架必须用正式档。**

|差异点|验证档（当前 v0\.37）|正式档（上架值）|为什么不同|
|---|---|---|---|
|任务唤醒 cadence|`INTERVAL_SECONDS = 660`（11 分钟）|`5280`（88 分钟）|验证期要在十几分钟内看到"跑没跑"|
|主动门禁间隔|J=20min / P=10min（降频翻倍 → 40 / 20min）|J=2h / P=100min（翻倍 → 4h / 200min）|同上；正式值对齐"不打扰"|
|proactive `delivery_mode`|`silent`（\+ 门禁通过时 Agent 显式发一条）|**同：****`silent`**<br>|`notify` 会在每次唤醒（含不发送）都投递结果 → 出戏消息。**两档都用 ****`silent`**|
|记忆整理 / 生活编造|`silent` \+ 不产生用户可见输出|同|避免每天刷群|
|安静时段|23:00–08:00|同|一致|
|未成年最低间隔|120min|同|一致|
|唤醒 ≠ 必发|唤醒只是"检查一次"；发不发由门禁决定|同|常见误解|

**切换方式（3 处常量 \+ 文档同步）**

1. `proactive-message/scripts/setup_schedule.py`：`INTERVAL_SECONDS = 88 * 60`；

2. 同上：`PROACTIVE_DELIVERY` **保持 ****`"silent"`**（平台不投递；要发由 Agent 显式发一条）；

3. `proactive-message/scripts/should_disturb.py`：`base_interval_min = 120 if mbti_letter == "J" else 100`；

4. 同步文档：`AGENTS.md`（创建契约表 \+ 说明）、`tools/README.md`、`proactive-message/SKILL.md`、`TESTING.md`。

> **口径演进说明**：v5 的 `silent` 是「应用自己发消息」时代的写法；v0\.37 一度改为「`notify` \+ Bot 自动投递最终回复」，实测发现**每次唤醒（含门禁不通过）都会投递结果** → 出戏消息。**v0\.38 定为 ****`silent`**** \+ 门禁通过时 Agent 显式发一条**：不发时零动静、要发时恰好一条。

**安全**：敏感词 5 类必过滤；主动消息的**热搜内容在生成前**先过滤；回复在**发送前**再过滤 \+ 阶段边界检查。

**已知局限（须上架前处理）**：安全词库为 demo 最小可用集，政治类须替换为合规权威源；只覆盖字面命中；用户输入侧目前不做输入过滤（仅回复侧过滤）。
